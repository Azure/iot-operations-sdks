# ADR 33: No SDK-level MGET for the State Store

## Context

Alongside the new `SCAN` API, an `MGET` API was proposed for the State Store
SDKs: pass the client a list of keys and get the values back in one call.

The State Store has no `MGET` command. Broker ADR 0092, "DSS Scan and MGET,"
decided not to add one, and said the SDKs would provide similar behavior by
sending several `GET` requests in parallel. This ADR revisits that SDK-side
decision only; the protocol decision stands.

The gap between what the `MGET` name suggests and what the SDK would actually do
is the root of the concerns below.

### Concerns

- **MGET is not a true State Store operation.** Because the State Store has no
  `MGET` command, an SDK-level `MGET` would need to use separate `GET` requests.
  The values may be read at different times, and data may change between
  requests. There would also be no single round trip or all-or-nothing result.
  The name may imply otherwise, and applications can build the same behavior.
- **Error and result behavior needs a permanent choice.** A key may be found,
  missing, or fail with an error. The API must decide whether to return as soon
  as one request fails or wait and return the outcome for every key. It must also
  define how repeated input keys are handled and whether each repeated key gets
  its own result. These choices become part of the public API.
- **We need to decide how the requests run and set limits.** The requests could
  run one at a time, all at once, or with a fixed number in progress. If the SDK
  sets that number, every application is bound by our choice. We may also need
  to limit how many keys are allowed in one call, such as 1,000 or 10,000. Broker
  ADR 0092 does not define either limit, and we do not have one value that is
  right for every application and deployment.
- **Large calls use more memory.** An API that returns all results together may
  need to keep many values and errors in memory until the call finishes.
- **Retries belong to the application.** A key can be absent, or its one `get()`
  can fail transiently. If the API doesn't retry, it adds little beyond separate
  `GET` requests. If it does retry, we own the count and backoff. Since `timeout`
  is per key, there is no single overall timeout, so the call may take much
  longer than the per-key timeout.
- **It's permanent public API for a small amount of application code.** Whatever
  we pick must be implemented, tested, and kept compatible across all three SDKs,
  while applications can provide the same behavior with bounded parallel
  requests.

## Options considered

### Option 1: Ship `MGET` as a helper

One `get()` per key, an internal parallel-request limit, no automatic retries,
one result per input key.

- Pro: simple for reading a small set of keys; safe parallelism implemented once.
- Con: the name suggests a real multi-key command, and we must define and keep
  the result shape, ordering, limits, timeout and cancellation behavior across
  all SDKs, with no strong basis for the values we'd choose.

### Option 2: Ship the helper under a different name

Something like `get_many`, with an application-supplied parallel-request limit,
documented clearly as sending a separate `GET` request for each key.

- Pro: avoids implying a real `MGET`, and lets each application pick a limit that
  fits its workload.
- Con: still permanent cross-SDK API wrapping a plain loop, and still forces us
  to settle result shape, ordering, duplicates, retries and cancellation.

### Option 3: Do not ship a helper; document the pattern

Keep multi-key reads in application code and provide samples showing how an
application can read multiple keys.

- Pro: no new API to keep aligned across SDKs; applications keep control of
  limits, retries, timeouts, cancellation and error handling.
- Con: applications write a small amount of code, and may over-parallelize if
  they don't follow the guidance.

## Decision

**Option 3.** We will not add `MGET` or `get_many` to the State Store SDKs.

We will provide cross-language samples for applications that need to read
multiple keys.

This supersedes only the SDK-side `MGET` helper decision in ADR 0092.

## Consequences

- The State Store SDK surface keeps matching real State Store operations; `SCAN`
  ships on its own.
- Applications needing multi-key reads send separate `GET`s. Data may change
  between those requests, so the values may come from different points in time.
- No helper API parity work or maintenance across the .NET, Go and Rust SDKs.
- We owe clear samples and guidance for applications that need to read multiple
  keys.
- We can revisit this decision if demand settles on one result shape, retry
  policy and concurrency model. We can then add a batch API under a name that
  doesn't imply Redis `MGET` behavior.
