# ADR 33: Defer an SDK-level multi-key GET API for the State Store

## Context

Alongside the new `SCAN` API, an `MGET` API was proposed for the State Store
SDKs: pass the client a list of keys and get the values back in one call.

The State Store has no `MGET` command. Broker ADR 0092, "DSS Scan and MGET,"
decided not to add one, and said the SDKs would provide similar behavior by
sending several `GET` requests in parallel. This ADR revisits that SDK-side
decision only; the protocol decision stands.

The gap between what the `MGET` name suggests and what the SDK would actually do
is the root of the concerns below.

### Concerns

- **MGET is not a true State Store operation.** Because the State Store has no
  `MGET` command, an SDK-level `MGET` would need to use separate `GET` requests.
  The values may be read at different times, and data may change between
  requests. There would also be no single round trip or all-or-nothing result.
  The name may imply otherwise, and applications can build the same behavior.
- **Error and result behavior needs a permanent choice.** A key may be found,
  missing, or fail with an error. The API must decide whether to return as soon
  as one request fails or wait and return the outcome for every key. It must also
  define how repeated input keys are handled and whether each repeated key gets
  its own result. These choices become part of the public API.
- **We need to decide how the requests run and set limits.** The requests could
  run one at a time, all at once, or with a fixed number in progress. If the SDK
  sets that number, every application is bound by our choice. We may also need
  to limit how many keys are allowed in one call, such as 1,000 or 10,000. Broker
  ADR 0092 does not define either limit, and we do not have one value that is
  right for every application and deployment.
- **The SDK would need to decide whether to retry failed requests.** A missing
  key is a successful result with no value and does not need a retry. A `GET`
  request can still fail because of a timeout, a State Store error, or an
  underlying protocol error. If `MGET` retries failed requests, the SDK must
  decide which errors to retry, how many times to retry, and how long to wait.
  Different applications may need different retry behavior.
- **Timeout behavior needs to be defined.** The existing `GET` timeout applies
  to one request. For multiple keys, the SDK must decide whether to apply that
  timeout to every `GET`, or treat it as one timeout for the whole `MGET` call.
  A whole-call timeout may need to be divided among the keys, while a per-key
  timeout may make the whole call take much longer. Different applications may
  need different timeout behavior.
- **It's a permanent public API for a small amount of application code.** Applications can
  build it using the existing `GET` API. Adding it to the SDK would require us
  to define and maintain the same behavior across all SDKs.

## Options considered

### Option 1: Add a multi-key GET API

Add an SDK API that sends one `GET` request for each key and returns the results
in one call. The API could be named `MGET` or `get_many`.

- `MGET` is a familiar name, but it may suggest that the State Store has a real
  multi-key command.
- `get_many` makes it clearer that this is SDK behavior built from separate
  `GET` requests.

- Pro: gives applications a convenient API and keeps the implementation
  consistent across SDKs.
- Con: the SDKs must define how missing keys, failed requests, duplicate keys,
  request limits, retries, timeouts and cancellation are handled.

### Option 2: Defer the API and document the pattern

Keep multi-key reads in application code and provide samples showing how an
application can read multiple keys.

- Pro: applications keep control of limits, retries, timeouts, cancellation and
  error handling.
- Pro: the SDKs can wait for clearer customer demand before choosing the API
  behavior.
- Con: applications write a small amount of code and may send too many `GET`
  requests at the same time if they do not set a limit.

## Decision

**Option 2.** We will not add `MGET` or `get_many` as part of the current State
Store SDK work. We will treat a multi-key GET API as lower-priority work and
revisit it when there is clearer customer demand and expected behavior.

We will provide cross-language samples for applications that need to read
multiple keys.

This updates the SDK-side decision in ADR 0092 by deferring the API. It does not
decide that the API should never be added.

## Consequences

- The State Store SDK surface keeps matching real State Store operations; `SCAN`
  ships on its own.
- Applications needing multi-key reads send separate `GET`s. A value may be
  updated after one `GET` finishes and before another one starts, so the results
  may not show the State Store at one exact point in time.
- We owe clear samples and guidance for applications that need to read multiple
  keys.
- A multi-key GET API remains possible as lower-priority work.
- If we add it later, we must choose its result shape, request limits, retry
  behavior, timeout behavior and name. A name such as `get_many` would make it
  clear that the SDK sends separate `GET` requests.
